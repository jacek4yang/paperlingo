# AGENTS.md — Authoritative Development Contract

This document is the authoritative contract for any human or AI agent working in this
repository. If another document conflicts with this one, this document wins.

## Project mission

PaperLingo is a Simplified-Chinese desktop application for native Chinese speakers who
read English academic papers. The user pastes an English sentence or paragraph, generates
a high-quality English prompt, runs it manually through a web AI (ChatGPT / Claude /
Grok / Gemini), pastes the JSON response back, and PaperLingo renders a focused learning
interface. Everything learned accumulates into a local SQLite knowledge base for
long-term review.

The workflow is deliberately manual and clipboard-based:

```
English text -> generate prompt -> copy -> user's web AI -> copy JSON -> paste -> parse -> learn
```

## Technology constraints (fixed)

- Python 3.13+ (consistently configured in pyproject.toml, ruff, and CI).
- PyQt6 + Qt Widgets is the UI stack. Never switch to QML, Electron, a web UI, PySide,
  or any other framework.
- `uv` is the only supported Python project/dependency runner. Never invoke `pip` or
  `python -m pip` directly.
- `sqlite3` from the Python standard library is the only database. Never add SQLAlchemy
  or another ORM/database layer.
- Pydantic v2 for AI response validation.
- pytest + pytest-qt for tests, ruff for lint, PyInstaller for packaging.

## Language contract (non-negotiable)

User-facing Simplified Chinese:

- Application UI, dialogs, buttons, error messages shown to the user, empty states,
  settings UI, learning explanations displayed by the application.
- `README.md` is entirely Simplified Chinese.
- Chinese strings used purely as UI resources are allowed and should be centralized
  where practical (e.g. a UI strings module) instead of scattered through business logic.

Developer-facing English:

- Source-code comments, docstrings, internal names, developer log messages,
  `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md`, GitHub issue/PR templates,
  GitHub Actions workflows, commit messages, PR titles and descriptions,
  architecture documents, build-script comments, repository description.

Generated LLM prompts:

- Every instruction generated by PaperLingo for an AI must be written in English:
  main analysis prompts, model-specific prompt profiles, repair prompts, schema
  instructions, learning-profile instructions, web-search instructions.
- The compiled prompt must instruct the AI, in English, to produce explanations in
  natural Simplified Chinese, and must use the English phrase "Simplified Chinese".
- Do not place Chinese examples or Chinese field descriptions inside prompt templates.
- JSON property names in prompts stay English; quoted source fragments must be
  preserved exactly.
- A repair prompt that embeds a raw AI response must encode the payload in an
  ASCII-safe representation (e.g. `json.dumps(value, ensure_ascii=True)`) so the
  repair instructions remain entirely English.
- A regression test asserts no CJK characters appear in compiled prompts for English
  input. Do not weaken this test.

## UI principles

- The primary reading workflow is sequential and minimal:
  1. Enter English (Step 1)
  2. Copy prompt / paste AI response (Step 2)
  3. Understand and learn (Step 3)
- The result view uses progressive disclosure: hero content first (original sentence,
  natural translation, core meaning, skeleton), then a segmented navigation
  (overview / structure / grammar / vocabulary / expressions / concepts) with a
  list-plus-detail interaction model.
- Sentence structure is interactive: clicking a segment shows its role and
  explanation. If an AI segment cannot be mapped reliably to the exact source text,
  do not highlight it. Never fuzzy-match aggressively enough to mis-highlight.
- Minimal visual language: large whitespace, one restrained accent color,
  low-saturation borders, ~12px card radius, consistent 8/12/16/24 spacing rhythm,
  no gradients, no rainbow color system, no glossy controls, no decorative emoji in
  navigation.
- Do not communicate meaning with color alone; keep text contrast strong.
- Internal UI values passed to the prompt compiler must be stable English identifiers
  (use `QComboBox.setItemData`), never Chinese display labels.
- Learning-status user labels: 认识 / 不熟 / 不会. Review rating user labels:
  忘记 / 困难 / 记得 / 熟练. Internal values stay English (`known` / `unfamiliar` /
  `hard`, `again` / `hard` / `good` / `easy`). Do not mix domain state and display
  text inconsistently.

## Database contract

- SQLite lives beside the executable when packaged: `<dir of PaperLingo.exe>\paperlingo.db`.
  In development, use a deterministic project-local path (derived from `__file__`).
  This portable contract overrides any AppData behavior. Do not reintroduce a
  user-configurable database path setting.
- If the database directory is not writable, show a clear Chinese user-facing error
  including the path and terminate cleanly. Never silently fall back elsewhere.
- Enable `foreign_keys` and `busy_timeout`; use WAL plus a durability setting
  appropriate for a small desktop app. On clean shutdown, checkpoint WAL.
- Database close must be idempotent, connected to `QApplication.aboutToQuit`, and
  protected by `try/finally` around the event loop.
- All SQL belongs in the database/repository layer. UI code must never execute raw SQL
  or touch `db.conn` directly.
- A successful analysis save plus knowledge ingestion must be atomic: explicit
  transaction boundaries; roll back on ingestion failure or use another explicitly
  documented atomic strategy. Do not silently swallow persistence errors.
- Word identity is normalized by lemma + meaningful part of speech. Do not merge
  unrelated senses merely because surface text matches. Occurrence counts must stay
  accurate.
- Schema changes require incrementing the database version and an explicit migration.
  Never destroy existing user databases; test upgrades from the current schema.
- Draft (unfinished reading state) persistence lives in SQLite, not a separate AppData
  JSON file.

## Security boundaries

- AI output is untrusted input. Never `eval` or `exec` AI output. Never render
  unescaped AI-provided HTML, CSS, or Markdown. All AI data flows through JSON
  extraction -> Pydantic validation -> domain model -> safe plain-text rendering.
- Any AI- or user-controlled string interpolated into program-generated HTML must be
  escaped (`html.escape`), or HTML must be avoided in favor of plain-text widgets.
- Never call `eval`, `exec`, or add direct model API integration in v0.1.0.
- Treat URLs as plain data. Only open a URL after explicit user interaction, and only
  for expected schemes (http/https). Never auto-load remote images or pages.
- Do not add API keys, browser automation, web scraping, OCR, cloud sync, or login.

## Architecture boundaries

- Layers: UI (PyQt6) -> domain models (Pydantic/dataclasses) -> prompt compiler /
  response parser -> repository/database -> learning/review scheduler.
- The prompt/profile layer owns all model-specific behavior. Do not scatter
  `if model == ...` through UI code.
- The review scheduler stays behind a stable `Scheduler` interface with persisted due
  times and review logs. Do not add a heavy dependency solely to claim FSRS support.
- Reusable widgets live in `ui/widgets/`; pages in `ui/pages/`. No giant QWidget
  containing the whole application; no dozens of abstraction-only files either.

## Testing requirements

- `uv run pytest` must pass before any merge.
- Regression coverage is required for: prompt language contract (no CJK in compiled
  English prompts, Simplified Chinese output requested, repair prompt contract),
  parser/JSON extraction/malformed input, Pydantic schema, database CRUD, transaction
  rollback, idempotent close, portable DB path, word deduplication, occurrence
  counting, history/settings/draft persistence, learning status, knowledge ingestion,
  unsafe HTML escaping, and UI smoke startup.
- Never delete a failing test to achieve green CI.

## Build requirements

- `scripts/build.ps1` must: verify uv, `uv sync --frozen`, ruff, pytest, remove old
  build/dist, run PyInstaller (one-folder), verify `dist/PaperLingo/PaperLingo.exe`
  exists, and perform a short executable smoke launch.
- Never package a development/user database, build caches, or test fixtures.
- PyInstaller packaging must not bundle a pre-existing `paperlingo.db`.

## Git workflow

- `main` is protected. After bootstrap, all feature work happens on feature branches
  through pull requests. No direct push to main.
- Commit messages and PR titles/descriptions are English. Use small logical commits
  (`fix: ...`, `feat: ...`, `refactor: ...`, `ui: ...`, `test: ...`, `docs: ...`).
- Never use `git reset --hard`, `git clean -fd`, force pushes, or branch-protection
  bypass without explicit user authorization. Never delete user work.
- Squash merge is preferred; merge commits and rebase merges are disabled.

## GitHub workflow

- Required status checks on main: `quality` and `windows-package` (strict).
- No human approval is required (single-developer repository); stale review dismissal,
  conversation resolution, and linear history are enforced.
- CI must run for pull requests targeting main and for pushes to main.

## Forbidden changes (scope creep for v0.1.0)

No direct model API integration. No browser automation. No PDF reader. No OCR.
No Zotero plugin. No cloud synchronization. No login system. No vector database.
No Electron. No QML rewrite. No pip usage. No new localization framework.

## Definition of done

A change is done when: ruff passes, pytest passes, the app launches and the affected
flow was manually validated in the GUI (in both light and dark themes when UI was
touched), packaging is verified for release-sensitive changes, the working tree is
clean, and the change reached main through a protected pull request.
